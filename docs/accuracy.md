# 정확도

> **현재 상태: 첫 실측 완료 (2026-10-03). 처리량·에러율은 목표 안, 지연은 목표 밖(30~45% 높게 예측).**
> 그래서 아직 "부하 테스트를 대체한다"고 주장하지 않는다. 결과와 원인 분석은 3장에 있다.

## 2. 실측 검증 방법

[spec.md 10장](spec.md#10-정확도-검증-계획)을 그대로 구현한 [하네스](../harness/README.md)로 한다.

```bash
node harness/run.mjs --calibrate 60,90,120 --validate 200,300 --fault
```


1. docker-compose 기준 환경: Spring Boot 주문·결제·재고, MySQL, Redis, RabbitMQ. 컨테이너마다 CPU·메모리 limit 고정.
2. 장애 주입: Toxiproxy(지연·단절), tc netem(손실·RTT). `load-sim k6`가 시나리오에서 k6 스크립트와 Toxiproxy 계획을 만든다.
3. 실측: k6 + Prometheus로 처리량, p50·p95·p99, 에러율, 풀 사용률, GC 정지, 서킷 상태.
4. 보정: **저부하 구간 지표만** 시뮬레이터에 넣는다. 서비스·DB·캐시의 기본 지연 배율, 네트워크 RTT 배율, DB 경합 곡선을 맞춘다.
   설정에 명시된 CPU 시간은 사실로 보고 바꾸지 않는다.
5. 비교: 고부하 구간을 예측하고 실측과 비교한다. 외삽 성능이 곧 부하 테스트 대체 능력이다.

## 3. 첫 실측 결과 (2026-10-03)

- 환경: Apple M2 Pro 노트북 + OrbStack, `harness/docker-compose.yml`(order 2 vCPU, payment·stock 1 vCPU, MySQL, Redis, RabbitMQ, Toxiproxy)
- 시나리오: [harness/scenarios/cascading.yaml](../harness/scenarios/cascading.yaml) — 상품 조회 80% / 주문 20%, 장애 실행은 40~80초 payments-db 지연(Toxiproxy +198ms)
- 워밍업 120 rps × 60초 → 보정 측정 30·60·120 rps × 40초 → 검증 200·300 rps × 60초 → 장애 실행 200 rps × 120초

### 보정에 쓴 지점

| rps | 실측 p50 | 실측 p99 |
|---:|---:|---:|
| 30 | 3.83ms | 37.9ms |
| 60 | 2.46ms | 27.9ms |
| 120 | 1.85ms | 19.6ms |
| (검증) 200 | 1.51ms | 16.2ms |
| (검증) 300 | 1.49ms | 16.7ms |

실제 시스템은 **부하가 늘수록 빨라졌다**(JIT 워밍업을 충분히 한 뒤에도). 저부하에서는 CPU·VM이 유휴 상태에서 깨어나는 비용이
요청마다 붙기 때문으로 보인다. 모델에는 이 효과가 없어 30 rps 지점을 넣으면 지연을 크게 잡는다. 아래는 60·120 rps로 보정한 결과다.

### 오차 (보정에 쓰지 않은 부하)

| 실행 | 처리량 (±10%) | 에러율 (±0.5%p) | p50 (±15%) | p99 (±15%) |
|---|---|---|---|---|
| 200 rps | 202 vs 200 (+1.0%) ✅ | 0% vs 0% ✅ | 2.1 vs 1.51ms (+42%) ❌ | 22.2 vs 16.2ms (+37%) ❌ |
| 300 rps | 300.8 vs 300 (+0.3%) ✅ | 0% vs 0% ✅ | 2.1 vs 1.49ms (+44%) ❌ | 22.2 vs 16.7ms (+33%) ❌ |
| 장애 (payments-db 지연) | 201.7 vs 200 (+0.8%) ✅ | 0% vs 0% ✅ | 2.2 vs 1.57ms (+41%) ❌ | 1309 vs 709ms (+85%) ❌ |

서킷브레이커는 실측과 시뮬레이션 모두 열리지 않았다(느린 호출 비율이 임계값에 닿지 않음).

### 해석과 다음 할 일

- **처리량·에러율·장애 시 정성적 거동(지연 폭증, 서킷 미개방)은 맞는다.** 지연은 일관되게 30~45% 높게 예측한다. 보수적인 쪽으로 틀린다.
- 저부하에서 느린 실제 시스템(유휴 복귀 비용)이 지연 보정을 끌어올린다. 보정 부하를 더 높이거나(60·90·120) 유휴 복귀 비용을 OS 모델에 넣어야 한다.
- 장애 실행의 p99 오차가 큰 이유: 시나리오의 장애는 "지연 ×100"이고 Toxiproxy에는 기준 지연에서 환산한 고정 지연(+198ms)으로 들어간다.
  보정으로 기준 지연이 바뀌면 둘이 어긋난다. 장애를 절대 지연(+200ms)으로 쓰는 방식을 추가해야 한다.
- 이 결과는 노트북 한 대에서 잰 것이다. 실제 서버(전용 코어, 고정 CPU 클럭)에서 다시 재야 한다.

목표치는 가설이다. 오차가 큰 시나리오도 숨기지 않고 "알려진 한계"로 남긴다.
알려진 모델 단순화는 [architecture.md](architecture.md#단순화와-알려진-한계)에 있다.
