# load-simulator 기획서

> 백엔드 물리엔진. 실제 MSA 설정을 넣으면 애플리케이션·OS·네트워크 3계층을 브라우저에서 순수 계산으로 시뮬레이션해,
> 부하 테스트 없이 한계 처리량과 장애 전파를 수 초 안에 보여준다.

이 문서는 원본 데모 기획서를 저장소용으로 정리한 것이다. 구현 현황은 [roadmap.md](roadmap.md),
엔진 설계는 [architecture.md](architecture.md), 입력 형식은 [model-reference.md](model-reference.md)를 본다.

---

## 1. 배경

[pretext](https://github.com/chenglou/pretext)는 브라우저 레이아웃(reflow)에 매번 묻던 텍스트 측정을 순수 계산으로 바꿔,
빠르기 때문에 가능한 새 UI를 열었다. 백엔드에서 "돌려봐야 아는" 대표는 **부하 테스트**와 **장애**다.

- 부하 테스트는 환경 구축에 며칠, 실행에 몇 시간이 든다.
- 장애 시나리오는 재현이 어렵다.
- 그래서 timeout, 재시도, 풀 크기 같은 설정은 대부분 감으로 정해진다.

## 2. 목표

1. **부하 테스트 대체** — 목표 SLO(예: p99 300ms, 에러율 0.1%)를 지키는 최대 처리량과 첫 병목 지점을 수 초 안에 산출한다.
2. **설정 비교** — timeout, 재시도, 서킷브레이커, 풀 크기를 슬라이더로 바꾸면 결과가 즉시 다시 계산된다.
3. **장애 전파 시각화** — 한 구간의 지연이 OS·네트워크·애플리케이션 계층을 타고 번지는 과정을 눈으로 보여준다.
4. **정확도 공개** — 실측 대비 처리량과 p99 오차를 수치로 공개한다. 1차 목표는 오차 10% 이내(가설, 검증으로 확정).

**하나의 시나리오, 두 가지 실행.** 같은 시나리오 파일로 시뮬레이션과 실제 부하 테스트를 모두 실행하고 결과를 나란히 비교한다.

## 3. 타겟 사용자와 핵심 사용 시나리오

1차 타겟은 부하 테스트 환경을 따로 갖추기 어려운 중소 규모 팀의 백엔드 개발자, 2차는 시스템 디자인을 학습하거나 면접을 준비하는 개발자다.

| 사용자 | 지금 겪는 문제 | 이 도구로 하는 일 |
|---|---|---|
| 서비스 백엔드 개발자 | 이벤트 오픈 전 "몇 RPS까지 버티나"를 부하 테스트 없이는 모른다 | 설정을 가져와 목표 트래픽에서의 p99와 첫 병목을 확인한다 |
| 온콜·SRE | 장애 회고에서 "설정을 바꿨다면"을 추측으로만 쓴다 | 장애 당시 트래픽을 재생하고 설정을 바꿔 결과를 비교한다 |
| 아키텍처 리뷰어 | timeout·재시도 설정이 서비스 간에 맞물리는지 검토할 방법이 없다 | 호출 그래프 전체의 재시도 증폭과 timeout 역전을 자동으로 찾는다 |
| 학습자 | 연쇄 장애·스탬피드를 글로만 배운다 | 예제 아키텍처에서 직접 장애를 일으키고 막아본다 |

핵심 사용 흐름은 세 단계다.

1. 설정을 가져오고(또는 블록으로 그리고)
2. 트래픽·장애 시나리오를 고르고
3. 슬라이더로 설정을 바꿔가며 결과를 비교한다.

## 4. 시뮬레이션 계층 구조

요청 하나의 지연 = 애플리케이션 계층의 대기·처리 시간 + OS 계층이 늘리는 시간 + 네트워크 계층이 더하는 시간.

세 계층은 따로 돌지 않고 엔진의 **사건 큐 하나를 공유**한다. 그래서 "GC 정지 → 스레드 점유 증가 → 상위 timeout → 재시도"처럼
계층을 넘나드는 연쇄가 그대로 재현된다.

### 4.1 애플리케이션·미들웨어 계층

모든 컴포넌트는 **"처리 슬롯 + 대기열 + 처리 시간 분포"** 의 조합으로 모델링하고, 슬롯과 대기열이 무엇을 뜻하는지만 컴포넌트마다 다르게 정의한다.

| 컴포넌트 | 슬롯 | 대기열 | 핵심 파라미터 | 꼭 재현할 동작 |
|---|---|---|---|---|
| 서비스 (Spring + Tomcat) | 워커 스레드 | accept 대기열 | threads.max, accept-count, 엔드포인트별 자체 처리 시간 | 하위 서비스를 동기 호출하는 동안 스레드를 붙잡는다 |
| 서비스 (WebFlux·가상 스레드) | 이벤트 루프 / 캐리어 스레드 | 없음(논블로킹) | 이벤트 루프 수, pinning 여부 | 블로킹 호출이 섞이면 루프 전체가 멈춘다 |
| DB 커넥션풀 (HikariCP) | 커넥션 | 풀 대기 | maximum-pool-size, connection-timeout | 풀 대기 시간 초과 시 예외 |
| DB 서버 (MySQL) | 동시 실행 쿼리 | 서버 대기 | max_connections, 쿼리별 지연, 경합 곡선 | 동시 쿼리가 늘수록 쿼리 하나의 지연이 늘어난다 |
| 캐시 (Redis) | 단일 명령 처리 스레드 | 클라이언트 대기 | 적중률, TTL, 명령별 지연 | TTL 동시 만료 시 DB로 몰리는 스탬피드 |
| 메시지 큐 (RabbitMQ / Kafka) | 컨슈머 × prefetch | 큐 / 파티션 | 발행 속도, 컨슈머 수, prefetch, ack 모드, DLQ | 실패 메시지의 무한 requeue, 컨슈머 지연 후 회복 |
| 외부 API | 상대 측 동시 처리량 | 없음 | 고정 지연 분포, 실패율, rate limit | 429 응답과 재시도의 상호작용 |

- 처리 시간은 평균 하나가 아니라 **분포**(로그정규 등)로 받는다. p99를 예측하려면 꼬리를 표현해야 하기 때문이다.
- 경합 곡선은 "동시성 1일 때 지연"과 "포화 시 지연" 두 점과 곡선 형태로 단순하게 시작한다.

### 4.2 API 단위 모델

시뮬레이션의 기본 단위는 서비스가 아니라 **API(엔드포인트)** 이고, 시스템에 포함된 모든 API를 한 번에 함께 돌린다.
실제 장애는 한 API가 공유 자원을 독점해 상관없는 다른 API까지 죽이는 형태로 자주 일어나기 때문이다.

**API 수집.** 사용자가 API를 일일이 입력하지 않도록 세 경로에서 자동으로 모은다.

| 출처 | 얻는 정보 | 비고 |
|---|---|---|
| Spring 소스 정적 분석 | `@RequestMapping` 계열 API, `@RabbitListener`·`@KafkaListener`, `@Scheduled`·Quartz 잡, Feign·RestClient·WebClient 호출 지점 | 트래픽이 없는 API까지 빠짐없이 찾는다 |
| OpenAPI 문서(springdoc) | API 목록, 요청·응답 크기 추정 | 소스 접근이 없을 때 대안 |
| OpenTelemetry 트레이스 | 실제 처리 시간 분포, API 간 호출 관계와 호출 횟수, 쿼리·캐시·메시지 발행 | 정적 분석 결과에 실측 수치를 덧입힌다 |

트레이스에 한 번도 나타나지 않은 API는 **"미관측"** 으로 표시하고 기본 프로파일을 쓴다. 사용자는 결과에서 어느 API가 추정값인지 항상 알 수 있어야 한다.

**API별 프로파일.** 자체 처리 시간 분포, CPU 시간, 메모리 할당량, 응답 크기, 하위 호출 목록. 하위 호출은 **확률과 횟수**를 포함한다
("재고 부족 시 30% 확률로 알림 API 호출", "상품 수만큼 반복 조회(N+1)").

**API 간 호출 그래프.** "주문 생성 API → 결제 승인 API → 결제 DB의 승인 쿼리" 같은 API·쿼리 단위 그래프로 요청을 흘린다. 회복성 정책도 이 그래프의 연결선마다 붙는다.

**트래픽 믹스.** 진입 API별 비율(예: 상품 조회 70%, 장바구니 20%, 주문 10%)을 게이트웨이 지표나 액세스 로그에서 자동 추출한다.
"조회 → 장바구니 → 주문" 같은 사용자 여정도 시나리오로 정의할 수 있다.

**공유 자원 경합.** 같은 인스턴스의 모든 API는 스레드풀, 커넥션풀, CPU, 힙을 공유한다. 비동기 작업(`@Async`), 메시지 리스너,
스케줄 배치도 같은 자원을 쓰는 참여자로 함께 시뮬레이션한다. ("관리자 리포트 API 하나가 커넥션풀을 독점해 주문 API까지 실패", "배치가 도는 동안 조회 API p99 상승")

**API별 결과.** 처리량, p99, 에러율, API별 SLO 충족 여부. 용량 산출은 "어떤 API가 가장 먼저 SLO를 깨는가와 그 원인 자원"을 답한다.

### 4.3 OS 계층

OS 계층은 애플리케이션이 **"스레드가 남아 있는데도 느려지는"** 이유를 설명한다.

| 자원 | 모델링 방식 | 핵심 파라미터 | 재현할 현상 |
|---|---|---|---|
| CPU | 코어 수만큼의 처리 슬롯, 요청별 CPU 시간 | vCPU 수, 요청별 CPU 시간, 컨테이너 CPU limit | 사용률 70% 이후 대기 시간 급증, cgroup 쓰로틀링으로 생기는 주기적 지연 |
| 스레드·컨텍스트 스위칭 | 실행 가능한 스레드 수 대비 코어 수로 오버헤드 계산 | 스레드 수, 스위칭 비용 | 스레드를 늘릴수록 처리량이 오히려 떨어지는 지점 |
| 메모리·GC | 요청별 할당량으로 힙 증가 속도 계산, 임계치에서 GC 정지 | 힙 크기, 요청별 할당량, GC 종류별 정지 시간 분포 | 부하가 오를수록 GC가 잦아지고, 정지 동안 모든 요청이 멈춘다 |
| 파일 디스크립터 | 열린 소켓·파일 수 카운터 | ulimit -n | 한도 도달 시 새 연결 수락 실패 |
| 커널 소켓 큐 | listen backlog와 accept 대기열 | somaxconn, tcp_max_syn_backlog | 큐가 차면 SYN 드롭 → 클라이언트 연결 지연(재전송 대기) |
| 임시 포트 | 아웃바운드 연결용 포트 풀, TIME_WAIT 유지 시간 | 포트 범위, TIME_WAIT 시간 | 커넥션 재사용 없이 호출하면 포트 고갈 |

**MVP는 CPU, GC, 커널 소켓 큐 세 가지만 구현한다.** 나머지는 2단계.

### 4.4 네트워크 계층

네트워크는 노드 사이의 **연결선(edge)에 붙는 속성**으로 모델링한다.

| 요소 | 모델링 방식 | 핵심 파라미터 | 재현할 현상 |
|---|---|---|---|
| 지연(RTT) | 구간별 RTT 분포 | 기본 RTT, 지터 | 동기 호출 깊이가 깊을수록 RTT가 누적된다 |
| 대역폭 | 구간별 전송 용량, 응답 크기로 전송 시간 계산 | 대역폭, 요청·응답 크기 | 큰 응답이 몰리면 전송 대기로 지연이 늘어난다 |
| 패킷 손실·재전송 | 손실 확률과 TCP 재전송 타이머(RTO) | 손실률, 최소 RTO | 1% 손실만으로 p99가 RTO(수백 ms) 단위로 튄다 |
| 연결 수립 | 새 연결마다 TCP·TLS 핸드셰이크 RTT 추가 | 핸드셰이크 RTT 수, keep-alive 여부 | 커넥션 재사용이 꺼져 있으면 호출마다 지연 증가 |
| HTTP 클라이언트 커넥션풀 | 대상 호스트별 커넥션 슬롯 | 최대 커넥션 수, 호스트당 한도 | 풀이 작으면 하위 서비스가 한가해도 호출 측에서 대기 |
| 로드밸런서 | 인스턴스 선택 알고리즘과 헬스체크 주기 | 라운드로빈·최소 연결, 헬스체크 간격·임계값 | 죽은 인스턴스로 헬스체크 주기 동안 요청이 계속 간다 |
| 장애 주입 | 시간 구간별 지연 배수, 손실률, 단절 | 시작·종료 시각, 강도 | 네트워크 파티션, 특정 AZ 지연 |

패킷 단위로 시뮬레이션하지 않는다. 요청 단위로 "이 호출에 추가될 네트워크 지연"을 분포에서 뽑는다.

### 4.5 회복성 정책

회복성 정책은 "A가 B를 호출할 때"의 설정이므로 **연결선에 붙인다.**

| 정책 | 파라미터 (Resilience4j·Spring 기준) |
|---|---|
| Timeout | 연결 timeout, 읽기 timeout, TimeLimiter |
| Retry | 최대 시도 수, 백오프(고정·지수), jitter, 재시도 대상 예외 |
| Circuit Breaker | 윈도우 종류(횟수·시간)와 크기, 최소 호출 수, 실패율 임계값, 느린 호출 기준 시간과 비율, OPEN 유지 시간, HALF_OPEN 허용 호출 수 |
| Bulkhead | 세마포어 또는 스레드풀 방식, 최대 동시 호출, 대기 시간 |
| Fallback | 대체 응답의 처리 시간, 캐시된 응답 사용 여부 |
| Rate Limiter | 주기별 허용 수, 대기 timeout |

**MVP부터 반드시 재현할 다섯 가지 동작**

1. **좀비 작업** — 호출자가 timeout으로 포기해도 피호출자는 끝까지 일한다. 이미 느린 DB에 부하가 계속 쌓인다.
2. **재시도 증폭** — 계층마다 재시도가 곱해진다. 3단 호출에서 각 3회 재시도면 최하위로 가는 요청이 최악의 경우 27배.
3. **timeout 역전** — 상위 timeout이 하위보다 짧으면 하위가 처리 중인데 상위가 포기하고 재시도해 일을 두 배로 만든다.
4. **HALF_OPEN 진동** — OPEN 유지 시간이 짧으면 회복 전 하위 서비스에 시험 호출이 반복되어 회로가 열고 닫히기를 되풀이한다.
5. **동기화된 재시도** — jitter가 없으면 실패한 요청들이 같은 순간에 재시도해 트래픽 파도가 생긴다.

엔진은 **정적 검사**도 수행한다. 시뮬레이션 전에 timeout 역전과 최대 재시도 증폭 배수를 호출 그래프에서 계산해 경고로 띄운다.

## 5. 부하 테스트 대체 기능

핵심 발상: **운영 트래픽 자체가 이미 공짜 부하 테스트 데이터다.**

1. **실측 보정(calibration)** — Micrometer·Prometheus 지표, OpenTelemetry 트레이스, DB 슬로우 로그로 엔드포인트별 처리 시간 분포, 호출 그래프, 쿼리 지연, 요청별 CPU 시간과 메모리 할당량을 자동으로 채운다.
2. **용량 산출** — SLO를 입력하면 트래픽을 이분 탐색으로 올려가며 SLO가 깨지는 RPS와 가장 먼저 포화되는 자원을 보고한다.
   예: "주문 API는 1,850 RPS에서 p99 300ms를 넘는다. 첫 병목은 payment-db 커넥션풀".
3. **시나리오 부하** — 이벤트 오픈 스파이크, 점진 증가, 장시간 지속(soak), 엔드포인트별 트래픽 비율. 기존 k6 스크립트를 가져와 재사용.
4. **배포 전 회귀 검사** — PR에서 설정·트레이스 프로파일이 바뀌면 CI에서 시뮬레이션해, 산출 용량이 기준 이상 떨어지면 실패. GitHub Action과 Gradle 플러그인으로 제공.
5. **결과 리포트** — 부하 테스트 리포트와 같은 형식(처리량, p50·p95·p99, 에러율, 자원별 포화도)으로 내보낸다.

**대체 범위**

| 상황 | 대체 여부 | 이유 |
|---|---|---|
| 설정 변경(풀 크기, timeout, 재시도, 인스턴스 수)의 영향 | 대체 가능 | 모델이 직접 다루는 변수다 |
| 같은 코드에서 트래픽 증가 시 용량 | 대체 가능 | 보정 데이터만 있으면 된다 |
| 새 기능·새 쿼리 추가 | 부분 대체 | 새 경로의 처리 시간은 스테이징에서 짧게 측정해 입력해야 한다 |
| 서비스 첫 출시(운영 지표 없음) | 부분 대체 | 기본 프로파일로 대략적인 범위만 추정한다 |
| 메모리 누수, 락 경합, 라이브러리 버그 같은 코드 결함 | 대체 불가 | 모델에 없는 동작이다 |

가장 큰 약점은 **외삽**이다. 평상시 낮은 부하의 지표만으로는 포화 근처의 경합 곡선을 알 수 없다.
그래서 제품의 기본 메시지는 **"실제 부하 테스트는 분기에 한 번 모델 검증용으로, 일상적인 질문은 시뮬레이터로"** 다.

## 6. 동일 시나리오 실측 실행

시나리오 파일 하나로 시뮬레이션과 실제 부하 테스트를 모두 실행하고 결과를 같은 화면에 겹쳐 비교한다.
권장 흐름은 **"탐색은 시뮬레이터, 확인은 실측"** — 설정 후보 수십 개를 시뮬레이터로 비교하고, 상위 2~3개만 실측으로 확인한다.

| 시나리오 요소 | 시뮬레이션에서 | 실측에서 |
|---|---|---|
| 트래픽 패턴·API 믹스·사용자 여정 | 사건 생성기 | k6 스크립트로 컴파일(arrival-rate 계열 executor) |
| 요청 본문·인증 | 불필요(크기만 사용) | 시나리오에 템플릿과 데이터셋으로 추가 |
| 지연·단절 장애 | 연결선 지연 배수 | Toxiproxy latency·timeout |
| 대역폭 제한 | 응답 크기로 전송 시간 계산 | Toxiproxy bandwidth, tc |
| 패킷 손실·RTT | 네트워크 지연 분포 | tc netem |
| CPU 경합 | 처리 슬롯 감소 | 컨테이너 CPU limit 조정 |
| 설정 변경(풀, timeout, 서킷브레이커) | 파라미터 즉시 반영 | Spring 설정 오버라이드(환경 변수) 생성 후 재배포 |
| SLO | 판정 기준 | k6 thresholds, 위반 시 자동 중단 |

- **지표 수집** — 실측 지표는 시뮬레이션과 같은 이름·단위로 수집한다. Micrometer와 함께 컨텍스트 스위칭 횟수, 네트워크 송수신 바이트, GC 정지 시간, listen 큐 넘침 횟수를 node_exporter·JVM 지표에서 모은다.
- **자동 비교와 보정** — 지표별 오차를 계산해 보여주고, 실측값으로 경합 곡선 같은 파라미터를 다시 맞춘다.
- **안전장치** — 대상은 허용 목록에 등록한 스테이징·전용 환경으로 제한하고, 운영 환경 대상 실행은 기본적으로 막는다. 최대 RPS 상한과 "에러율이 기준을 넘으면 즉시 중단" 조건을 필수 입력으로 둔다.

## 7. 데모 시나리오

모든 시나리오는 **"문제가 터지는 장면"과 "슬라이더 하나로 막는 장면"** 을 한 화면에서 보여준다.

| # | 시나리오 | 터지는 장면 | 막는 장면 | 계층 | 단계 |
|---|---|---|---|---|---|
| 1 | 결제 DB 지연 → 연쇄 장애 | 결제 서비스 스레드 고갈, 주문 서비스까지 전체 다운 | 서킷브레이커를 켜면 주문 서비스는 fallback으로 생존 | 앱 | MVP |
| 2 | 재시도 폭풍 | 3단 호출 각 3회 재시도로 최하위 트래픽 27배 | 재시도를 최상위 한 곳으로 모으고 jitter 적용 | 앱 | MVP |
| 3 | 이벤트 오픈 용량 산출 | 트래픽 10배 스파이크에서 p99 폭증 | 용량 산출 결과대로 인스턴스·풀 조정 후 SLO 유지 | 앱·OS | MVP |
| 4 | GC 일시정지 연쇄 | 부하 증가로 GC가 잦아지며 p99가 주기적으로 튐 | 힙·인스턴스 조정, 할당량 감소 효과 비교 | OS | 2단계 |
| 5 | 소켓 backlog 넘침 | SYN 드롭으로 클라이언트 연결이 1초 단위로 지연 | somaxconn·accept 대기열 조정 | OS·네트워크 | 2단계 |
| 6 | 패킷 손실 1% | 평균은 그대로인데 p99만 RTO 단위로 튐 | timeout·재시도 정책을 손실 특성에 맞춤 | 네트워크 | 2단계 |
| 7 | 캐시 스탬피드 | TTL 동시 만료 순간 DB로 요청 폭주 | TTL jitter, 단일 갱신(lock) 적용 | 앱 | 2단계 |
| 8 | 큐 컨슈머 지연과 회복 | 컨슈머 장애 후 큐 깊이 급증, 회복 시간 | 컨슈머 수·prefetch 조정으로 회복 시간 단축 | 앱 | 2단계 |
| 9 | 헬스체크 공백 | 죽은 인스턴스로 헬스체크 주기 동안 요청 유입 | 헬스체크 간격과 재시도 대상 조정 | 네트워크 | 3단계 |

## 8. 화면 구성과 인터랙션

한 화면에 **아키텍처 캔버스 + 설정 패널 + 지표 타임라인** 세 영역을 두고, 어떤 설정을 바꾸든 0.5초 안에 세 영역이 모두 다시 그려지는 것이 목표다.

| 영역 | 내용 | 주요 인터랙션 |
|---|---|---|
| 아키텍처 캔버스(중앙) | 서비스·DB·캐시·큐 블록과 연결선, 요청 입자의 흐름 | 블록 추가·연결, 입자가 쌓이는 곳이 곧 병목, 블록 색으로 포화도 표시 |
| 계층 토글(캔버스 상단) | 앱 / OS / 네트워크 보기 전환 | OS 보기는 노드 안의 CPU·GC·소켓 큐 게이지, 네트워크 보기는 연결선의 RTT·손실률 |
| 설정 패널(우측) | 선택한 블록·연결선의 파라미터 | 슬라이더와 숫자 입력, 변경 즉시 재계산 |
| 지표 타임라인(하단) | 처리량, p50·p99, 에러율, 서킷 상태 | 시간 구간 드래그로 확대, 특정 시점 클릭 시 그 순간의 캔버스 상태로 이동 |
| 비교 모드 | 설정 A와 B를 나란히 실행 | 두 타임라인을 겹쳐 그려 차이를 강조 |
| 용량 산출 패널 | SLO 입력과 결과 | "최대 RPS + 첫 병목" 한 줄 요약, 병목 블록 강조 |

**공유 기능이 데모 확산의 핵심이다.** 아키텍처, 설정, 시나리오, 난수 시드를 URL 하나에 담아 누구나 같은 결과를 재현할 수 있게 한다.

## 9. 엔진 아키텍처와 기술 스택

엔진은 **이산 사건 시뮬레이션(DES)** 으로 만들고, 렌더링과 완전히 분리된 순수 함수 `simulate(model, scenario, seed) → result`로 유지한다.

- **사건 처리** — "요청 도착", "처리 완료", "timeout", "GC 시작·종료", "서킷 상태 전이" 같은 사건만 시간순 우선순위 큐로 처리한다.
- **결정성** — 시드를 고정한 난수만 사용한다. 같은 입력이면 항상 같은 결과.
- **계층 결합** — 애플리케이션 사건의 처리 시간을 OS 계층(CPU 대기, GC 정지)과 네트워크 계층(RTT, 재전송)이 늘린다. 세 계층이 한 사건 큐를 공유한다.
- **시각화 분리** — 지표는 엔진이 전체 요청으로 정확히 계산하고, 화면의 입자는 샘플링한 대표 요청만 그린다.
- **용량 산출** — 같은 엔진을 트래픽만 바꿔 여러 번 실행해 이분 탐색한다. 실행이 빠르다는 전제가 이 기능의 성립 조건이다.

| 영역 | 선택 | 이유 |
|---|---|---|
| 엔진 | TypeScript, Web Worker에서 실행 | 설치 없이 브라우저에서 동작, UI 스레드를 막지 않음 |
| 엔진 고도화 | Rust → WASM (필요 시) | 순수 함수 인터페이스를 유지해 엔진만 교체 |
| 캔버스 편집 | React Flow | 블록·연결선 편집 기능을 바로 사용 |
| 입자 렌더링 | PixiJS (WebGL) | 수천 개 입자를 60fps로 그림 |
| 지표 차트 | uPlot | 대량 시계열을 가볍게 그림 |
| CLI·CI 실행 | Node.js 패키지 + GitHub Action, Gradle 플러그인 | 같은 엔진을 서버 측에서 재사용 |
| 검증 하네스 | Spring Boot 서비스, docker-compose, k6, Toxiproxy | 실측 대비 정확도 측정 |

입력은 **선언형 YAML 하나로 통일**하고, 캔버스 편집과 양방향으로 동기화한다.
가져오기는 application.yml(Tomcat, HikariCP, Resilience4j), OpenTelemetry 트레이스, Prometheus 지표, k6 스크립트 순으로 지원한다.

```yaml
nodes:
  order:
    kind: service
    runtime: { threads: 200, acceptCount: 100 }
    os: { vcpu: 2, heap: 2g, gc: g1, somaxconn: 4096 }
    endpoints:
      POST /orders:
        selfTime: { dist: lognormal, p50: 8ms, p99: 40ms }
        calls: [ "payment:POST /payments/approve", "order-db:insertOrder", "stock:GET /stocks/{id} x items" ]
edges:
  order->payment:
    network: { rtt: 1ms, loss: 0.1% }
    timeout: 2s
    retry: { max: 3, backoff: exponential, jitter: true }
    circuitBreaker: { failureRate: 50, slowCall: 1s, window: 100, openFor: 10s }
scenario:
  traffic: { type: spike, base: 500rps, peak: 5000rps, at: 60s, mix: { "GET /products": 70%, "POST /carts": 20%, "POST /orders": 10% } }
  faults:
    - { at: 90s, target: payment-db, latencyX: 10 }
  slo: { p99: 300ms, errorRate: 0.1% }
```

## 10. 정확도 검증 계획

"부하 테스트를 대체한다"는 주장은 실측과의 오차를 공개해야만 성립한다. **검증 하네스를 엔진과 같은 비중의 산출물로 만든다.**

1. **기준 환경 구축** — docker-compose로 Spring Boot 서비스 3개(주문·결제·재고), MySQL, Redis, RabbitMQ. 컨테이너마다 CPU·메모리 limit 고정.
2. **장애 주입** — Toxiproxy로 지연·손실·단절, tc netem으로 패킷 손실과 RTT.
3. **실측** — k6로 데모 시나리오별 트래픽, Prometheus로 처리량, p50·p95·p99, 에러율, 풀 사용률, GC 정지, 서킷 상태 수집.
4. **보정** — 저부하 구간의 지표만 시뮬레이터에 넣어 파라미터를 채운다.
5. **비교** — 고부하 구간을 시뮬레이터로 예측하고 실측과 비교한다. 외삽 성능이 곧 부하 테스트 대체 능력이다.
6. **리포트 공개** — 시나리오별 오차표를 README와 문서 사이트에 공개하고, 하네스도 오픈소스로 공개한다.

| 지표 | 1차 목표 오차 | 비고 |
|---|---|---|
| SLO 한계 RPS | ±10% | 부하 테스트 대체의 핵심 지표 |
| p99 지연 | ±15% | 꼬리 지연은 분포 모델 정확도에 민감 |
| 첫 병목 자원 | 일치 | 틀리면 결과 전체가 무의미 |
| 서킷 OPEN 시점 | ±2초 | 장애 시나리오 재현 정확도 |

목표치는 가설이며 첫 검증 결과를 보고 확정한다. 오차가 큰 시나리오는 숨기지 않고 "알려진 한계"로 문서화한다.

## 11. MVP 범위와 마일스톤

MVP는 **데모 시나리오 1~3을 실측과 맞는 수치로 보여주는 것**까지다. 각 단계는 정해진 게이트를 통과해야 다음으로 넘어간다.
MVP의 API 입력은 YAML로 직접 쓰되, 여러 API의 트래픽 믹스와 공유 자원 경합은 처음부터 지원한다.
3단계가 끝나면 실제 서비스 한 곳에서 보정과 검증을 거쳐 "부하 테스트 대체" 주장을 공개한다. 일정은 아직 정하지 않았다.

마일스톤과 게이트, 현재 진행 상황은 [roadmap.md](roadmap.md)에서 관리한다.

## 12. 리스크와 미결정 사항

가장 큰 리스크는 **"예쁘지만 틀린 장난감"** 으로 보이는 것이고, 대응은 검증 수치의 공개다.

| 리스크 | 영향 | 대응 |
